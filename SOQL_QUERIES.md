# SOQL_QUERIES.md

Every SOQL query Valentine runs against Salesforce, plus the bulk
existence-check recipes built on the same patterns. Read-only throughout — no
query here writes. Source of truth is `src/connectors/salesforce.ts`; this
file is a human-readable map of it and is regenerated by hand when that
connector changes.

All queries assume a REST session (`Authorization: Bearer <token>`) against
`{instanceUrl}/services/data/v59.0/query?q=<url-encoded SOQL>`. The connector
uses API `v59.0`; the ad-hoc bulk recipes below use `v60.0` — either works,
pick one and stay on it.

## Auth and session

A static access token, or a **sid command** that prints a fresh one: any shell
command whose last stdout line is a valid access token. The connector runs it
lazily on first use and once more on a `401` / `INVALID_SESSION_ID`, so the
session self-refreshes as long as a browser tab stays logged in. Config keys:
`salesforceKey` (static) or `salesforceSidCommand` (`VALENTINE_SALESFORCE_SID_COMMAND`).

An auth failure that survives one retry is **thrown**, so a sweep reports
"couldn't reach Salesforce" (ambiguous), never a false "clean". A restricted
object or field instead degrades to no-match — that is a data-model gap, not an
outage, and every sub-fetch is wrapped so one missing object never sinks the
rest.

## Two conventions that recur

**Probe tiers.** Some queries try a rich field set, and on `INVALID_FIELD` /
`No such column` / `FIELD_INTEGRITY` drop to a smaller one and remember the
working tier for the rest of the process. This is how Valentine stays
data-model-agnostic: an org without a managed package answers the probe once
and never pays for it again. Two probes exist — Account firmographics and
Opportunity deal fields.

**The non-admin `ORDER BY` restriction.** `ActivityHistories` and
`OpenActivities` are relationship-only sub-queries (neither can be queried at
the top level). For a non-admin user Salesforce demands *exactly* these
`ORDER BY` clauses:

- `ActivityHistories`: `ORDER BY ActivityDate DESC, LastModifiedDate DESC`
- `OpenActivities`: `ORDER BY ActivityDate ASC, LastModifiedDate DESC`

Anything else — even adding `NULLS LAST` — returns `MALFORMED_QUERY`
"implementation restriction". Live-verified 2026-09-18.

## 1. Connection check (`whoami`)

```sql
SELECT Name FROM Organization LIMIT 1
```

Some orgs restrict the `Organization` sObject (`INVALID_TYPE`) even for users
who can read `Account` fine, so a failure here falls back to the instance
hostname rather than failing the whole connection.

## 2. Company search — `Account`

`where` is `Website LIKE '%<domain>%'` for a domain, or `Name LIKE '%<name>%'`
for a name. Probe-tiered on the field list:

**Tier 0 — with ZoomInfo firmographics:**

```sql
SELECT Id, Name, Website, OwnerId, Owner.Name, Owner.IsActive, LastActivityDate,
       NumberOfEmployees, AnnualRevenue, Industry,
       ZoomInfo_Employees__c, ZoomInfo_Annual_Revenue__c, ZoomInfo_Primary_Industry__c,
       (SELECT Id FROM Contacts LIMIT 6)
FROM Account WHERE <where> LIMIT 10
```

**Tier 1 — standard (drops the `ZoomInfo_*` columns):**

```sql
SELECT Id, Name, Website, OwnerId, Owner.Name, Owner.IsActive, LastActivityDate,
       NumberOfEmployees, AnnualRevenue, Industry,
       (SELECT Id FROM Contacts LIMIT 6)
FROM Account WHERE <where> LIMIT 10
```

**Tier 2 — bare (drops firmographics entirely):**

```sql
SELECT Id, Name, Website, OwnerId, Owner.Name, Owner.IsActive, LastActivityDate,
       (SELECT Id FROM Contacts LIMIT 6)
FROM Account WHERE <where> LIMIT 10
```

A domain result is then **host-filtered in code** (see the bulk recipes): the
`LIKE` is a coarse net, the host compare is what makes `hines.com` not match
`machines.com`.

## 3. People search — `Contact`

`where` is `Email LIKE '%@<domain>'` for a domain, or `Name LIKE '%<name>%'`.

```sql
SELECT Id, Name, Email, AccountId, Account.Name,
       OwnerId, Owner.Name, Owner.IsActive, LastActivityDate
FROM Contact WHERE <where> LIMIT 10
```

## 4. People search — unconverted `Lead`

Runs alongside the Contact search. `where` is
`(Email LIKE '%@<domain>' OR Website LIKE '%<domain>%')` for a domain, or
`(Name LIKE '%<name>%' OR Company LIKE '%<name>%')`.

```sql
SELECT Id, Name, Company, Email, Website, Status,
       OwnerId, Owner.Name, Owner.IsActive, LastActivityDate
FROM Lead WHERE IsConverted = false AND <where> LIMIT 10
```

## 5. Notes — `Note`

Per matched record (`ParentId` is the Account/Contact id):

```sql
SELECT Title, Body FROM Note WHERE ParentId = '<id>' ORDER BY CreatedDate DESC LIMIT 25
```

## 6. Logged calls / emails — `Task` (as outcome text)

`rel` is `WhatId` for a company, `WhoId` for a person. Task subjects often
carry the outcome ("passed, too early"):

```sql
SELECT Subject, Description FROM Task WHERE <rel> = '<id>' ORDER BY CreatedDate DESC LIMIT 10
```

## 7. Pipeline — `Opportunity` (company context)

Probe-tiered on the deal-shape fields:

**Tier 0 — with CRE custom fields:**

```sql
SELECT Id, Name, StageName, IsClosed, Amount, CloseDate, Probability, Type, Owner.Name,
       Size__c, Size_Type__c, Term_Months__c, Lease_Type__c
FROM Opportunity WHERE AccountId = '<id>' ORDER BY CreatedDate DESC LIMIT 10
```

**Tier 1 — standard deal fields (drops `*__c`):**

```sql
SELECT Id, Name, StageName, IsClosed, Amount, CloseDate, Probability, Type, Owner.Name
FROM Opportunity WHERE AccountId = '<id>' ORDER BY CreatedDate DESC LIMIT 10
```

**Tier 2 — bare:**

```sql
SELECT Id, Name, StageName, IsClosed
FROM Opportunity WHERE AccountId = '<id>' ORDER BY CreatedDate DESC LIMIT 10
```

## 8. Pipeline — `CampaignMember` (contact context)

```sql
SELECT Id, CampaignId, Campaign.Name, Status FROM CampaignMember WHERE ContactId = '<id>' LIMIT 10
```

## 9. Linked people — `Contact` (company context)

```sql
SELECT Id, Name FROM Contact WHERE AccountId = '<id>' LIMIT 5
```

## 10. Activity — `ActivityHistories` + `OpenActivities` (the "last touched" / "next step")

Both are relationship sub-queries off the parent (`<sobject>` is `Account`,
`Contact`, or `Lead`). Note the mandatory `ORDER BY` clauses above.

```sql
SELECT Id,
       (SELECT Id, Subject, ActivityDate, ActivityType, IsTask
        FROM ActivityHistories ORDER BY ActivityDate DESC, LastModifiedDate DESC LIMIT 5),
       (SELECT Id, Subject, ActivityDate, ActivityType, IsTask, Status, Owner.Name
        FROM OpenActivities ORDER BY ActivityDate ASC, LastModifiedDate DESC LIMIT 5)
FROM <sobject> WHERE Id = '<id>' LIMIT 1
```

`ActivityHistories` newest-first is the last touch; `OpenActivities`
soonest-first is what someone already has scheduled ("Glenn already has a call
on 2026-10-01 — coordinate").

## Bulk existence checks (Attio ⇄ Salesforce)

Valentine sweeps one target at a time. To answer "which of my Attio companies
already exist in Salesforce" for the whole book, batch the same patterns. Two
independent match keys, so a hit on either is real and a hit on both is
certain.

### Key 1 — domain host-match (broad `LIKE`, exact host filter)

SOQL has no regex and no exact-domain field, so match broadly at the DB and
tighten in code. **Batch 100 domains per query**; `LIKE` clauses are cheap and
100 fits well under SOQL's 100k-char and the URL length limits.

```sql
SELECT Id, Name, Website, LID__LinkedIn_Company_Id__c
FROM Account
WHERE Website LIKE '%acme.com%' OR Website LIKE '%willdan.com%' OR ...   -- 100 OR'd
LIMIT 2000
```

Then in code, keep only rows whose **Website host equals the domain or a
subdomain of it**:

```python
def host(u):
    u = (u or "").strip().lower().split("//")[-1].split("/")[0]
    return u[4:] if u.startswith("www.") else (u or None)

def is_match(sf_website, attio_domain):
    h = host(sf_website)
    return bool(h) and (h == attio_domain or h.endswith("." + attio_domain))
```

This is the accuracy guarantee: the broad `LIKE` returned ~190 raw rows for 150
domains in testing; the host filter cut it to 85 real matches, dropping every
`machines.com`-for-`hines.com` substring hit.

**Truncation is the real accuracy risk, not false positives.** A batch
containing a common substring (`comcast.com` and its many child accounts) can
exceed the `LIMIT` and silently drop real matches. Guard it with a recursive
split — if a batch returns exactly the `LIMIT`, halve it and re-run each side:

```python
def run_chunk(chunk, depth=0):
    recs = batch_query(chunk)            # the OR'd Website LIKE query above
    if len(recs) >= LIMIT and len(chunk) > 1 and depth < 6:
        mid = len(chunk) // 2
        return run_chunk(chunk[:mid], depth + 1) + run_chunk(chunk[mid:], depth + 1)
    return recs
```

### Key 2 — LinkedIn company id (exact integer, zero false positives)

Both systems carry LinkedIn's numeric organization id: Salesforce
`LID__LinkedIn_Company_Id__c` (from the Sales Navigator package; `string(80)`
but in practice bare digits), Attio `linkedin_company_id_1749270669`
(a `number`). They agree on companies present in both — 17 of 20 in a sample,
the 3 disagreements being multinationals whose two systems picked adjacent
subsidiary pages. It is only populated on **188 of 326,130** Salesforce
accounts, so use it as a **confirming** key, not the primary one:

```sql
SELECT Id, Name, LID__LinkedIn_Company_Id__c
FROM Account WHERE LID__LinkedIn_Company_Id__c IN ('50628','2467','3681', ...)
```

`IN (...)` is an exact match, so no host filter is needed — but coverage is thin.
The combined check treats a Salesforce row as a match when **either** its
Website host equals the Attio domain **or** its LinkedIn id equals the Attio
company's id; a row matching both is the highest-confidence tier.

### Enriching matches with the Ownership Desk's 18 Account fields

Once the domain match has the Salesforce account ids, pull the full field set
the salesforced Ownership Desk shows, batched by `Id IN (...)` (200 ids/query):

```sql
SELECT Id, Name, Website, Type, OwnerId, Owner.Name, Account_Owner_s_Email__c,
       Account_Owner_Territory_s__c, LastActivityDate, Inactivity_Date__c,
       BillingCity, BillingState, BillingCountry,
       ZoomInfo_Number_of_Locations__c, Portfolio_Locations__c, of_Locations__c,
       NumberOfEmployees, AnnualRevenue
FROM Account WHERE Id IN ('001…','001…', …) LIMIT 200
```

Friendly CSV column names: `sf_id, sf_name, website, account_type, owner_id,
owner, owner_email, owner_territories, last_activity, inactivity_date, hq_city,
hq_state, hq_country, zi_locations, portfolio_locations, num_locations,
employees, annual_revenue`. The custom fields (`Inactivity_Date__c`,
`Account_Owner_s_Email__c`, `Account_Owner_Territory_s__c`, the three
`*_Locations__c`) are org-specific — probe-tier them and drop to a bare set
(`Id, Name, Website, OwnerId, Owner.Name, LastActivityDate`) on `INVALID_FIELD`,
same as the account firmographics probe. Verified present on the cresa org
2026-09-24. The playground's Bulk domain check returns these 18 per matched
account, and the enriched columns carry into the review CSVs.

### Dedup fallout

The host-match surfaces domains that map to **more than one** Salesforce
account — real duplicates, or one bad `Website` value shared across records
(e.g. `merrillcorp.com` on both "Merrill Lynch" and "Merrill Gardens"). Collect
these as a cleanup list; they are a Salesforce data-quality signal, not a
Valentine bug.

### What can and cannot be bulk-checked this way

| Valentine signal | Bulk existence check? | How |
|---|---|---|
| Company in Salesforce | **Yes** | `Website LIKE` batch + host filter (key 1) |
| Company by LinkedIn id | **Yes**, thin coverage | `LID__LinkedIn_Company_Id__c IN (...)` (key 2) |
| Contact / person by email domain | **Yes** | `Email LIKE '%@domain'` batched the same way |
| Unconverted Lead by domain | **Yes** | `Lead WHERE IsConverted = false AND Website LIKE`/`Email LIKE`, batched |
| Owner, last-activity date | **Yes**, same query | add `OwnerId, Owner.Name, LastActivityDate` to the batch `SELECT` |
| Firmographics (employees/revenue/industry) | **Yes**, same query | add the tier-0 columns; drop on `INVALID_FIELD` |
| Open opportunity / stage | **No, not in one batch** | `Opportunity.AccountId` needs the Account ids first — two-step: match accounts, then `WHERE AccountId IN (...)` |
| Notes / task outcomes | **No, not in one batch** | `Note.ParentId` / `Task.WhatId` are per-record; batch by `ParentId IN (...)` after you have the ids |
| Activity history / next step | **No** | `ActivityHistories`/`OpenActivities` are per-parent sub-queries; one parent id each |

The rule of thumb: anything keyed on a **field of the record** (Website, Email,
LinkedIn id, Owner, dates, firmographics) batches into one `WHERE ... OR ...` or
`... IN (...)`. Anything keyed on a **parent id** (opportunities, notes, tasks,
activities) needs the ids first, then a second `WHERE <FK> IN (...)` batch.
